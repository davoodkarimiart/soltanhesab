# تحویل، دیباگ و انتشار سلطان حساب | 2026-10-22

**وضعیت:** `hesabsvo` (سورس اجرایی) در GitHub روی نسخه `0.6.25` است. سایت فعلی در **هاست تست** و در مرحله دریافت نظر مشتری است؛ هیچ Stable نهایی یا نصب واقعی روی هاست جدید تأیید نشده است.

## هنگام گزارش باگ از مشتری

1. نسخه `VERSION` و دامنه/محیط (تست یا نهایی)، زمان دقیق رخداد با منطقه زمانی، نوع دستگاه/مرورگر را ثبت کنید.
2. مسیر بازتولید را بنویسید: شرکت، پنل، گزارش/ترانسفر مرتبط، مرحله‌ای که کاربر زده، خروجی مورد انتظار و نتیجه واقعی. **شناسه** را ثبت کنید؛ فایل‌های مالی یا اطلاعات خصوصی را در GitHub عمومی نگذارید.
3. برای خطاهای مالی، مقایسه `Member Win` خام، علامت، نرخ‌های Snapshot، درصد، جمع دریافتی/پرداختی، اختلاف Excel، دوره تسویه و سابقه اصلاح را با fixture ناشناس انجام دهید. هیچ مبلغی نباید صرفاً برای رفع خطای UI تغییر کند.
4. Developer می‌تواند صفحه `index.php?page=health` را بررسی کند (دیتابیس، migrations، writable dirs و برخی dependencyها).
5. لاگ‌های JSON-lines موجود: `storage/logs/error.log`, `storage/logs/system.log`, `storage/logs/audit.log`. فعلاً دسترسی از طریق فایل‌منیجر خصوصی هاست/SSH است؛ **پنل جست‌وجوی کامل لاگ هنوز پیاده/تأیید نشده است**.
6. لاگ‌ها ممکن است توضیح داخلی داشته باشند: پیش از اشتراک‌گذاری، همه نام‌ها، آدرس‌ها، secrets، tokenها و اطلاعات مشتری را حذف کنید. خطاهای تولیدشده نباید stack trace را به مشتری نشان دهند؛ `app.debug=false`.
7. یک تست رگرسیون مرتبط اضافه کنید و فقط پس از تأیید روی کپی محیط، پچ محدود و مستند ارائه دهید.

## دروازه Stable و استقرار جدید

- [ ] بازخورد مشتری بسته و صاحب پروژه نسخه را تأیید کند.
- [ ] گزارش روزانه، ریز مشتری، تجمیعی، خروجی اکسل ۲۰۱۰ و اندروید، PDF و تصاویر و رسیدهای ترانسفر روی داده آزمایشی مقایسه شوند.
- [ ] گزارش دارای مغایرت دلاری و دلیل استثنا، هشدار ترانسفر، محاسبه هفتگی/ماهانه، جلوگیری از هم‌پوشانی و ابطال/ویرایش تست شوند.
- [ ] سورس کامل با commit/tag در `hesabsvo` ثبت شود؛ فایل `VERSION`، release notes، SQL migrations و تست‌ها مطابق هم باشند.
- [ ] روی هاست آزمایشی مقصد PHP 8.1+ و افزونه‌های لازم، HTTPS، مسیرهای نوشتنی و MySQL/MariaDB بررسی شود.
- [ ] با **دیتابیس خالی** نصب از `/install/` اجرا شود؛ ساخت schema، ساخت Admin/Developer، قفل installer، login و عملیات مالی و export واقعی آزمایش شود. داده‌های قبلی برای نصب **خالی** لازم نیستند.
- [ ] بکاپ/بازیابی و rollback روی نمونه امن تمرین شود و مکانیزم بکاپ کافی پیش از انتقال مشتری تعیین شود.
- [ ] سیاست نگهداری log، خطاهای production و دسترسی developer بازبینی شود.

## مواردی که هنوز در نقشه راه مانده‌اند

فاز ۱۰: پنل Developer چندبخشی، نمایش/جستجوی Audit/System/Error، تنظیم retention، بکاپ دستی/زمان‌بندی cPanel، تست ارسال تلگرام، نگهداری نسخه محلی و retry، بازیابی کنترل‌شده با ثبت Audit.

فاز ۱۱: MCP مبتنی بر همان Application Services با token hash/scope, revoke, expiry و ثبت audit.

فاز ۱۲: تست خودکار چندلایه، امنیت، نصب/ارتقا/rollback و تأیید نهایی release.

**اشتباه رایج:** موجود بودن فایل Logger یا صفحه Health به معنی تمام‌شدن Phase 10 نیست. همین‌طور حاضر بودن /install/ به معنی موفقیت نصب واقعی روی هاست مقصد نیست.
